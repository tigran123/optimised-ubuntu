# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A small toolkit of Bash scripts for deploying a custom, performance-optimized Ubuntu 26.04 LTS system onto portable storage (SSD / image file). The produced disk boots on **both** UEFI and legacy BIOS machines from a single GPT layout. There is no application code — the deliverable is the scripts plus the methodology documented in `README.md` and `Portable-SSD-README.md`.

## Running the scripts

There is no build, test, lint, or CI setup — scripts are run directly and require `sudo` (they shell out to `parted`, `mkfs`, `losetup`, `chroot`, `grub-install`, etc.). Always preview destructive runs with `--dry-run`, which prints every wrapped command instead of executing it. Run with no arguments (and no `TARGET`/`TGT_*` in the environment, which would be a legitimate env-var-driven invocation) and it prints `--help` instead of marching into Phase 1 and failing on the *default* source path.

- **`install.sh`** — the single, universal entry point. Source can be a unified block device, a `.img` file (auto-attached via `losetup -P`), or scattered source partitions (`--source-efi/-root`, which may live on different disks, plus `--source-boot`); target can be a unified device (it partitions + formats) or scattered partitions (`--target-efi`/`--target-root` required, `--target-bios-boot`/`--target-boot` optional). **`/boot` inside `/` is the default layout, and a separate `/boot` is *explicit* on both sides** — only `--source-boot` says a source has one, only `--target-boot` gives a target one, and nothing is ever inferred from a partition table: a `/boot` partition a disk happens to carry is left alone unless it is named. The two sides are independent, so all four combinations work, and either layout converts to the other (`--no-target-boot` folds a source's separate `/boot` into the target's root, `--target-boot` splits it back out). It earns its keep on a machine whose BIOS cannot boot from NVMe: BIOS Boot, the ESP and `/boot` go on a SATA disk the BIOS can read, while `/` — everything the running system actually reads — stays on the four-times-faster NVMe. Where the source has a separate `/boot` and the target is described partition by partition, one of `--target-boot`/`--no-target-boot` is *required* rather than guessed; Phase 3 also cross-checks the mounted source's fstab against `--source-boot` in both directions before anything is copied. Roles are found by GPT type GUID and filesystem label (`scan_disk_roles()`), never by partition number, so any other partition on either disk — data, swap, another distro, an obsolete `boot`-labelled one — is none of the script's business. Each role is left in place (target == source), migrated (target differs → reformat + full copy), or — under `--update` — synced (target differs → keep the existing filesystem, `rsync --delete` onto it). `--update` subsumes the old disk-to-disk clone (`backup.sh`, removed): it refreshes an already-installed clone incrementally instead of rebuilding it. `--exclude-from FILE` passes `rsync --exclude-from`, omitting listed paths from the copy (e.g. an impersonal clone); combined with `--update` it also adds `--delete-excluded`, so those paths are purged from the target rather than protected. If the file lists the system's swap file (as `exclude-personal.txt` does), that swap file is dropped rather than re-created and its fstab entry is commented out — an exclude file builds a deliberately swapless minimal disk. Its paths are paths in the *source's root filesystem* — the thing rsync is actually handed — so a rule naming a directory the source binds in from elsewhere matches nothing at all, and `exclude_rules_unmatchable()` names every such rule in the summary rather than let an "impersonal" clone quietly ship the SSH keys the file believes it strips. It reports three kinds and stays silent about nothing: a rule whose data is in the transfer under another name (the one that matters), a rule whose data is off the root filesystem — *not* the same as harmless, since a mount the target keeps still carries it on the booted clone — and a rule whose wildcard falls above its last component, which no mount point can be matched against and so is declared unchecked rather than passed. `EXCLUDE_PROBED` is what keeps "not checked" distinguishable from "nothing to report", an empty audit being what both look like. **The regenerable browser caches are dropped by default** (`--keep-cache` copies them): `~/.cache/google-chrome` is an HTTP cache, a compiled-JS cache and a shader cache and nothing else, while everything that matters — passwords, cookies, bookmarks, extensions — lives in `~/.config/google-chrome` and is copied either way. **The ESP is the one role that is never copied:** GRUB is installed onto it with its boot directory *there* (`--boot-directory=/boot/efi/boot`, for legacy BIOS and UEFI alike), and the menu that lives there is shared by every rootfs on the disk — each install writes only its own `entries/<root-uuid>.cfg` and rebuilds the master over whatever entry files are present. The **memory tester** is the one menu item belonging to no rootfs at all: `sync_esp_memtest()` copies the target's own `/boot/mt86+x64` (Ubuntu's `memtest86+` package) to `boot/grub/memtest/` on the ESP, and the master offers it whenever that image is present. That is what lets one disk carry a rootfs per machine (desktop, laptop, iMac) behind a single ESP, each 64 GB slot holding just its platform-specific state with `/home/tigran`, `/usr/local` and the rest bind-mounted out of a shared `/data`. **`--keep-efi`** is what makes that repeatable: it keeps the ESP's filesystem and UUID instead of reformatting it, so adding a second slot does not wipe the first system's menu entry or invalidate the ESP UUID in its fstab. `--target-root-label NAME` labels the slot's root filesystem NAME instead of `root` (`mkfs.ext4 -L` when it is formatted, `e2label` when `--update` keeps it, refused for an in-place root) — which tells the slots of such a disk apart in `lsblk` but does *not* make the disk scannable, since `root` remains the only label `scan_disk_roles()` looks for. `--brand NAME` overrides the GRUB menu branding; without it, `--update` keeps the brand already stamped into the target's `/etc/default/grub` (probed via a transient read-only mount before rsync overwrites the file, so it also shows under `--dry-run`), and only otherwise is the reported model of the disk holding the target rootfs used (which can be a USB card reader's name instead of the card's).
  ```bash
  # Fresh 3-partition disk (BIOS Boot, ESP, root):
  ./install.sh --image Ubuntu26-Portable-16GB.img --target /dev/sda
  ./install.sh --image Ubuntu26-Portable-16GB.img --target /dev/sda --dry-run
  # Deploy from the running machine's own disk. nvme0n1 also carries a large
  # data partition; it is ignored, because root is found by its 'root' label:
  ./install.sh --source /dev/nvme0n1 --target /dev/sdd --update
  # Incrementally sync a split-disk source (sda EFI + nvme root) onto sdb:
  ./install.sh --source-efi /dev/sda2 --source-root /dev/nvme0n1p1 \
               --target-bios-boot /dev/sdb1 --target-efi /dev/sdb2 \
               --target-root /dev/sdb3 --update
  # The old-BIOS layout: BIOS Boot, ESP and /boot on sda (all pre-existing),
  # / on the NVMe. Splitting /boot out of an image's unified root:
  ./install.sh --image Ubuntu26-Portable-16GB.img \
               --target-bios-boot /dev/sda1 --target-efi /dev/sda2 \
               --target-boot /dev/sda3 --target-root /dev/nvme0n1p1
  # ...and folding that machine back onto an ordinary 3-partition disk:
  ./install.sh --source-efi /dev/sda2 --source-boot /dev/sda3 \
               --source-root /dev/nvme0n1p1 --no-target-boot \
               --target-bios-boot /dev/sdb1 --target-efi /dev/sdb2 \
               --target-root /dev/sdb3
  # Add a rootfs slot to a disk that already boots one: keep the shared ESP
  # (and register this system in the menu on it), format only sde5:
  ./install.sh --image Ubuntu26-Portable-16GB.img --keep-efi \
               --target-bios-boot /dev/sde1 --target-efi /dev/sde2 \
               --target-root /dev/sde5 --brand Laptop --target-root-label laptop
  # Impersonal clone — deploy minus the paths listed in exclude-personal.txt:
  ./install.sh --image Ubuntu26-Portable-16GB.img --target /dev/sda \
               --exclude-from exclude-personal.txt
  ```

Verifying a change: there's no test harness, so validate by running the script against a throwaway `.img` (create one with `truncate`/`dd`, attach with `losetup -P`) under `--dry-run` first, then for real against a loop device or scratch disk.

## Architecture

`install.sh` is a single self-contained script (the former `portable-common.sh` library was folded into it, and the `init-disk.sh`/`backup.sh` helpers were removed). It sets `set -euo pipefail` and defines the `run()` dry-run wrapper (it quotes args with `%q`).

The pipeline:

1. **Resolve source/target topology** — unified device, image (loop), or scattered partitions. `scan_disk_roles <disk> <PREFIX>` scans a whole disk and fills `<PREFIX>_BIOS/_EFI/_ROOT` by GPT type GUID (`GUID_BIOS`/`GUID_EFI`/`GUID_LINUX`, defined near the top of the script) and filesystem label. Root is the Linux partition labelled `root` (which this toolkit's own `mkfs` writes by default); failing that, a *lone* unlabelled Linux partition. The label the scan keys on is the literal `root` and nothing else: `--target-root-label` changes what the `mkfs` writes, never what the scan reads, so a rootfs given any other label is thereafter reachable only by `--source-root`/`--target-root` — deliberately, since the disks that want per-machine labels are the multi-slot ones that are always addressed partition by partition anyway. **Everything else on the disk is ignored** — a data partition, a swap, another distro's rootfs, or a `boot`-labelled partition (skipped explicitly, since it is certainly not a root filesystem and should not make the disk look ambiguous). **`/boot` is a role again, but never a *discovered* one:** `scan_disk_roles()` fills only `_BIOS/_EFI/_ROOT`, and a separate `/boot` exists only because `--source-boot`/`--target-boot` named it. **Ambiguity is an error, never a guess:** two or more unlabelled candidates with no `root` label dies naming them and pointing at `--source-root`/`--target-root` or `e2label` — and so does more than one partition *labelled* `root`, which is the layout of a disk carrying a rootfs per machine and is therefore always addressed partition by partition. Both are old bugs made fatal: an earlier version claimed the first unclaimed Linux partition as `/boot`, which silently adopted a 721 GB data partition (and on a non-`--update` run would have `mkfs.ext4 -L boot`'d it), and let the *last* `root`-labelled partition win, so `--target /dev/sde --update` would have synced onto whichever slot `lsblk` happened to list last. It is used for a unified source **and** for a unified `--target` under `--update`, where the existing layout must be discovered rather than imposed (a fresh `--target` instead gets the canonical `p1`/`p2`/`p3`). Individually-named partitions are checked with `validate_partition_type()`. In a dry run no loop device is attached, so `scan_image_roles_dryrun()` reads an image's partition table with `parted -sm` straight out of the file (no root, no loop); it cannot see filesystem labels there (parted's name field is the GPT partition name, `primary` for everything this toolkit creates), so it takes the *first* Linux partition as root and warns when there is more than one candidate — it only feeds the dry run's printed summary. Any target role that is currently mounted (or active swap) is refused up front — a second mount of an in-use filesystem would succeed and let the sync write into it.
2. **Prepare target** — `parted` GPT layout (BIOS Boot 1 MiB, then the ESP — 256 MiB unless `--target-efi-size` says otherwise — then root to 100%) + `mkfs`, skipped per-role for in-place roles and skipped under `--update` (which keeps the existing filesystems and `rsync --delete`s onto them) — all but the root filesystem's *label*, the one piece of metadata `--target-root-label` still stamps on a filesystem that is kept, with `e2label`, before anything is mounted and without disturbing its UUID. The ESP is formatted when `FORMAT_EFI` says so — i.e. when it is not already the source's and neither `--keep-efi` nor `--update` was given; `--keep-efi` is in turn *rejected* with a fresh unified `--target`, whose ESP has just been created by `parted` and holds no filesystem to keep, and an ESP that is not formatted is checked to be `vfat` up front (not just under `--update`) rather than failing on the mount halfway through. `--target-efi-size` only reaches `parted`, so it is *rejected* rather than silently ignored under `--update` or with individual `--target-*` partitions; its `k`/`M`/`G` suffixes denote a size (bare = MiB) and must resolve to whole MiB, since root starts where the ESP ends. **`parted` never creates a `/boot` partition** — a fresh unified `--target` gets exactly those three, and `--target-boot` is rejected with a unified `--target` for that reason: it names a partition that must already exist. `MIGRATE_BOOT` then decides whether it is `wipefs`+`mkfs.ext4 -L boot -i 32768 -m 0 -E lazy_itable_init=0,lazy_journal_init=0 -O sparse_super2`'d (target differs from source, or the source had none) or left in place.
3. **Mount + sync** — mounts target RW (`$MNT`, then `$MNT/boot` when `TGT_SEP_BOOT`, then `$MNT/boot/efi`; without `--target-boot`, `$MNT/boot` is an ordinary directory) and source RO (`$SRC`, …), then a per-role `rsync -ahHAX --inplace --numeric-ids -x --verbose` (one rsync per migrated/synced filesystem) with the live-filesystem exclusions on root. **There is no EFI pass:** the ESP is generated, never copied — everything on it is written by Phase 5's `grub-install` and `write_esp_menu()`, and rsyncing the source's would import a master menu whose entries name the *source* disk's root filesystems, burying the entries of the other systems that boot from a shared ESP. **`-S` is deliberately absent** and only `--sparse` adds it back: every hole rsync punches is one more entry in the file's ext4 extent tree, and a large VM image is perforated by thousands of tiny ones. Measured on a 51.8 GiB `.vdi` (`/usr/local/bin/sparse_mapper.py`, which walks it with `SEEK_DATA`/`SEEK_HOLE`): 12,309 holes, 82% of them ≤ 64 KiB and worth 0.137 GiB between them, 1.01 GiB saved in total — 2% of the file — in exchange for ~11,900 extra extents. That pushed the extent tree from one level to two (a 4 KiB leaf block holds 340 entries, the inode's root holds 4), so every `fsck.ext4 -f` offered to optimize it and every read walked the extra level; fully allocated the same file needs ~415 extents, purely from the 128 MiB per-extent cap. Across the whole 459 GiB source root, sparseness was worth 1.36 GiB (0.3%). Writing the nulls out costs a couple of percent more I/O — don't reinstate `-S` as the default. Every command in this phase — the mounts and the rsyncs alike — goes through `run()`, so a dry run prints the exact command lines rather than a one-line summary: the assembled option set is the thing worth reviewing before committing to a multi-hour transfer. Only the parts that need the mounted source are skipped in a dry run (`scan_swapfiles`/`scan_cache_drops`/`rebuild_swapfiles`), and `MOUNTS_DONE` stays 0 so `cleanup()` has nothing to unmount — but the printed command is still the command that runs: `swap_excludes_from_preview()`/`cache_filters_from_preview()` rebuild the per-swap-file `--exclude=` and the per-cache `--filter='H …'` from what the pre-gate probe already read off its transient read-only mount, and only a probe that could not read the source at all (an image, with no loop device attached) makes them announce what the command is missing instead. The shared `RSYNC_OPTS` array gains `--delete` only under `--update`, `--exclude-from=FILE` when `--exclude-from` is given, and `--delete-excluded` when both apply (so excluded paths are purged from, not protected on, the target). Because `--exclude-from` paths are anchored to each transfer root, the personal `/…` paths in the file only match during the root rsync.
   `/boot` gets a pass of its own only when it has to. `BOOT_PASS` is 0 in exactly two cases — `/boot` inside `/` on both sides (an ordinary directory riding along with the root rsync) and the same partition on both sides (in place) — and 1 otherwise, including both conversions. `-x` keeps the root transfer out of the target's mounted ESP at `$MNT/boot/efi` — it stops the sender crossing the boundary *and* stops `--delete` recursing across it on the receiving side. `BOOT_FILTERS` does the same job for `/boot` whenever it is a filesystem of its own on *either* side (`TGT_SEP_BOOT || BOOT_PASS`, wider than "gets a pass", so an in-place `/boot` is protected too), and it takes **two** rules — `--filter='- /boot/'` hides it from the sender, and the explicitly receiver-side `--filter='P /boot/'` is what stops `--delete` emptying the target's `/boot`, since `--delete-excluded` (added when `--update` and `--exclude-from` combine) demotes unqualified rules to sender-side only. The `/boot` pass protects `/efi/` the same way, because `$MNT/boot` may be a plain directory rather than a mount point that `-x` would shield.
   Right after the source root is mounted, `fstab_mounts_boot "$SRC/etc/fstab"` cross-checks the real layout against `--source-boot` **in both directions**: an unnamed separate `/boot` means the root rsync copies an empty mount point and the target ends up with no kernel, while a `--source-boot` the source does not actually use would be mounted over the real `/boot` and ship an empty one. The source's own fstab is the authority (whatever its partition table looks like), and it can only be read once mounted — so a dry run announces that it cannot check this. The source `/boot` is then mounted when `BOOT_PASS` — and only then, now that there is no EFI pass to need `$SRC/boot/efi`. For an in-place `/boot` that mount is a `mount --bind "$MNT/boot"`: the filesystem is already mounted read-write there, so a second read-only mount of it is redundant at best, and refused outright by a kernel that will not give one superblock both flags.
   Swap **files** are the one thing never transferred: the file is one multi-gigabyte run of zeros, so copying it ships gigabytes over a slow link to produce what `fallocate` makes from metadata alone — and under `--sparse`, `-S` would punch it full of holes and `swapon` then refuses it at boot (`skipping - it appears to have holes`). `scan_swapfiles()` reads the source's fstab (`swapfile_entries()` picks out plain-path `swap` entries — devices, `UUID=`, zram are ignored), puts each one through `fstab_realpath()` — **only a swap file on the source's root filesystem is this run's business**, since only that filesystem is mounted at `$SRC` and only it is in the rsync; `/data/swap` on a `/data` partition is skipped with one line saying so, because re-creating it would `fallocate` gigabytes into the *root* filesystem under a directory the target mounts `/data` over at boot (invisible, unusable, never reclaimed) and Phase 4 would then disable the very fstab entry that named it. The same walk finds the transfer path of a swap file that *is* in the copy but under another name behind a bind, which is what `SWAPFILE_REAL` carries and what the `--exclude=`, the `fallocate` and the verify all use, while `SWAPFILES`/`SWAPFILES_DROPPED` keep the *fstab* paths that `rewrite_fstab()` matches on. It then excludes each remaining one from the root rsync, and asks rsync itself — `swapfile_excluded()`, a one-file `--dry-run` against a deliberately non-existent destination so the quick check can't skip an already-synced file — whether an `--exclude-from` rule drops it. Kept ones are re-created afterwards by `rebuild_swapfiles()` (`rm` + `fallocate` to the source file's exact size + `chown`/`chmod 600` + `mkswap`, preserving the source's label and UUID); dropped ones are neither copied nor re-created, since an exclude file is used to build a deliberately swapless minimal disk. All of that happens in Phase 3, *after* the confirmation gate, so `probe_source_swapfiles()` runs the same `swapfile_entries()`/`swapfile_excluded()` pair over a transient read-only mount of the source root beforehand and fills `SWAP_PREVIEW`: the summary would otherwise print "swap: none" about a disk that is about to receive a multi-gigabyte swap file. It is skipped when `MIGRATE_ROOT` is 0 (no root transfer means no rebuild) and degrades to "could not be read here" when the source root is not a mountable block device — a dry run against an image, which has no loop device attached.
   Regenerable **browser caches** are the other thing not transferred, and the reason is the same shape: `~/.cache/google-chrome` (948 MB in 21,539 files on the reference machine) is `Default/Cache`, `Default/Code Cache` and a shader cache, all of which Chrome rebuilds on demand, while the profile that holds the passwords and cookies is `~/.config/google-chrome` and is copied like anything else. Finding them is the interesting part, because **the transfer's namespace is not the running system's**: rsync gets the source's root filesystem raw, with none of its bind mounts replayed, so on a slot-per-machine disk the cache is at `/var/local/tigran-state/cache/google-chrome` and `/home/tigran/.cache/…` names nothing. `cache_drop_paths()` therefore lists candidates in the *running* system's namespace (`/root/.cache`, every `/home/*/.cache`, any `.cache` the fstab mounts) and translates each through `fstab_realpath()`, which walks the source's own fstab bind by bind and reports whether the result is on the root filesystem at all — a `.cache` bound in from the data partition is not in the transfer, so there is nothing to drop. When it is not, `fstab_realpath()` prints the mount point that stopped the walk instead of the translation, which is how the exclude audit can name the filesystem those rules landed on (a caller reading it through a command substitution cannot be told through a global). `fstab_mount_table()` is what it walks: one `<mountpoint>\t<fs|bind>\t<source>` row per fstab entry, with trailing slashes stripped, `rbind` counted as a bind, and an octal-escaped path (`\040`) announced and skipped rather than emitted as a row that could never match. The rule is `--filter='H <path>/'` and **not** `--exclude=`: an exclude is also a receiver-side *protect*, so under `--update`'s `--delete` the stale cache already on the target would survive, which is the exact opposite of the point. Hide is sender-side only, so the target's copy goes the way of everything else the source no longer has — the mirror image of the `- /boot/` + `P /boot/` pair, which wants precisely the protection that would be wrong here. `CACHE_FILTERS` is passed *first* on the rsync command line, so a `+` line in an `--exclude-from` file cannot re-include what `--keep-cache` is the documented way to keep. `scan_cache_drops()` is the Phase 3 pass; `probe_source_layout()` resolves the same list (and audits `--exclude-from`) before the gate, off the mount `probe_source_swapfiles()` already holds, and `cache_filters_from_preview()` reuses it so even a dry run prints the real rules. Both go through `cache_filters_for()`, so the two paths cannot drift, and every path is `rsync_pattern_escape()`d first: a rule is a pattern, and a directory really called `a[bc]` would otherwise be hidden as a character class matching directories that were never probed — and, under `--update`'s `--delete`, removed from the target.
4. **Translate identifiers** — `rewrite_fstab()` rewrites old→new UUIDs and reconciles the `/boot` entry with the target's layout. Three moving parts, all decided before the awk runs: `map_boot` (translate the boot UUID only when the source really had a separate `/boot` — otherwise `OLD_UUID_BOOT` *is* `OLD_UUID_ROOT` and the boot substitution would rewrite the root entry before the root substitution ever saw it), `sep_boot` = `TGT_SEP_BOOT`, and `has_boot` (does the fstab just copied from the source carry a live `/boot` entry?). With `!sep_boot`, an inherited `/boot` entry is disabled *before* the substitutions, which would otherwise rewrite it into a bogus "mount the root filesystem at `/boot`" line; with `sep_boot && !has_boot`, one is inserted directly after the `/` entry — **never appended**, since `mount -a` walks fstab in order and a `/boot` line after `/boot/efi` would mount the ESP onto the bare directory and bury it. Comment lines are passed through untouched, *before* the foreign-UUID disabler: Ubuntu's stock fstab header mentions `UUID=`, and an earlier version tagged it `# [PORTABLE-SYNC-DISABLED]` on every single sync. The disabled-line handler also un-tags a payload that is itself a comment, so an fstab already damaged that way heals on the next sync. It also comments out the entries of swap files dropped by `--exclude-from` (so a swapless disk does not boot into a failing `swapon`), retargets the existing UUID-based swap entry to `NEW_UUID_SWAP` in place (appending one only if none exists, and dropping stale disabled swap lines), and comments out foreign mounts / binds (tagged `# [PORTABLE-SYNC-DISABLED]`, never re-prefixed on later syncs) — but **keeps what still resolves**, which is what makes a disk of per-machine rootfs slots sharing one `/data` survivable. The awk therefore runs in **two passes over the same file**: pass 1 decides every device-backed mount (a UUID line is kept when `target_disk_uuids()` — `lsblk` over `target_disks()`, the de-duplicated parent disks of `TGT_ROOT`/`TGT_EFI`/`TGT_BOOT` — finds that UUID on a disk this run writes to, since such a filesystem is present exactly when this system is; another machine's disk still gets disabled, because a clone that boots elsewhere must not block on a device that is not there), then the binds are resolved in file order (authoritative: `mount -a` walks fstab in order) against the *longest matching* surviving mount point, each resolved bind joining the table so a bind riding another bind is judged by the one it rides on; pass 2 emits. So `/data` on the target's own disk survives with all ten `/data/… → /home/tigran` binds, and on a clone to a foreign disk `/data` is disabled and its binds go down with it while `/var/local/… → /home/tigran/.config` (rooted on `/`) survives. The `/tmp → /var/tmp` special case is gone: `/tmp` is a kept `tmpfs` entry, so the general rule keeps it. A swap **file** follows its carrier by that same rule — `/data/swap` under a disabled `/data` is unreachable, and leaving the entry live boots the target into a failing `swapon -a` — but only when pass 1 actually judged that carrier, so an unrecognised path (and any swap *device*) is left alone rather than guessed at. **Every line the awk disables is recorded** — kind, mount point, reason — into a temp file (`FSTAB_REPORT`, swept by `cleanup()` if the run dies mid-rewrite) that `report_fstab_disables()` renders immediately afterwards: five mounts can leave a booting system's fstab in a single run, a `/data` on the source's own disk plus every bind hanging off it, and until this existed the only way to find out was to read the file afterwards. A UUID row names the device that UUID resolves to *here* — almost always a partition of the source disk — and the `target_disks()` it is not on. Lines that arrived already tagged are never recorded, so an `--update` re-sync of a disk installed this way stays quiet instead of re-announcing them every time; a dry run never reaches Phase 4 at all and says so. `rewrite_grub_distributor()` stamps the resolved brand (`--brand` override, the target's pre-sync `GRUB_DISTRIBUTOR` value under `--update` — read by `probe_target_brand()` right after lock acquisition — or the target disk model) into the GRUB menu branding.
5. **Chroot + bootloader, then the shared menu** — `run_chroot_block()` bind-mounts `/dev /dev/pts /proc /sys /run` and installs GRUB for **both** `i386-pc` (BIOS) and `x86_64-efi --removable` (UEFI), each with **`--boot-directory=/boot/efi/boot`**: GRUB's boot directory lives on the **ESP**, so one prefix and one menu serve both firmware paths and belong to the *disk* rather than to whichever rootfs was installed last. That is what lets one disk carry a rootfs per machine behind a single ESP. **Nothing writes a routing stub any more** — with the boot directory on the ESP itself `grub-install` embeds a device-relative prefix in the image, which is why such an ESP holds `EFI/BOOT/BOOTX64.EFI` and *no* `EFI/BOOT/grub.cfg` (a stale one from an older version is deleted). `update-grub` still regenerates the rootfs's own `/boot/grub/grub.cfg`, which nothing boots from but which keeps the system self-describing, followed by `update-initramfs -u -k all`.
   The menu itself is written afterwards, on the host, by `write_esp_menu()`. Layout on the ESP: `boot/grub/grub.cfg` (the master), `boot/grub/entries/<root-uuid>.cfg` (one file per registered rootfs), `boot/grub/memtest/mt86+x64` (the memory tester, one per disk), `boot/grub/custom.cfg` (optional, hand-written, sourced last) and the module directories. **An install owns exactly one entry file and never edits another system's**; the master is rebuilt over whatever entry files are present, ordered by title, each `source` line guarded by `if [ -f … ]` so a hand-deleted entry retires that system instead of breaking the menu for the others. `set timeout=`/`set default=` are carried over from the existing master (5 and 0 only when writing one from scratch), so the last system installed never redefines the menu for the rest. The master also sets up **graphics**, guarded on `loadfont $prefix/fonts/unicode.pf2`: `insmod all_video` + `insmod gfxterm` + `set gfxmode=auto` + `terminal_output gfxterm`. This is not cosmetic. With no video driver loaded, GRUB under UEFI falls back to the firmware's own text console — the 80x25 box in the middle of a large panel, with whatever the firmware last drew still visible around it — and, less visibly, has no mode to hand to what it boots, so `grub_linux_setup_video()` fails and the EFI path leaves `have_vga = 0`. BIOS hides both faults behind VGA text mode, which UEFI does not have, which is why a menu that looked merely ugly under UEFI also made the memory tester die with its own `No graphics display found`. `all_video` resolves to `efi_gop` on one path and `vbe`/`vga` on the other, so one block serves the single master both firmwares read. The master also carries the **memory tester** when `boot/grub/memtest/mt86+x64` is on the ESP — one `menuentry` running `set gfxpayload=640x480,keep` then `linux $prefix/memtest/mt86+x64`, needing no `search` and no ESP UUID because `$prefix` carries its own device. The `gfxpayload` is doing two jobs. There must *be* a framebuffer to hand over — memtest86+ has no VGA text mode to fall back on under UEFI, and without one prints `No graphics display found` and stops — and it should be a *small* one, because the tester draws a fixed **640x400** panel and never scales it, so in a 2560x1440 framebuffer it sits in a rectangle in the middle. 640x480 is the smallest standard mode that holds it (the display then upscales); `keep` is the documented list fallback for firmware that does not offer it, preserving the mode gfxterm already set. Both terms verified on legacy BIOS and UEFI. `sync_esp_memtest()` puts the image there from the target's freshly-synced `/boot` (right for both layouts, since `/boot` is mounted at `$MNT/boot` either way), skipping when the source has no `memtest86+` installed or when the target's `/etc/default/grub` sets `GRUB_DISABLE_MEMTEST=true` — Ubuntu's own knob, read with `grub_default_value()`. It **adds or refreshes, never removes**: the ESP is shared, so a slot that does not want the tester must not unregister it for the slots that do, exactly as an install owns one entry file and carries `set timeout` over rather than redefining it. The image is a *disk*-level fact, so the master's block is driven by what is on the ESP rather than by what this run's source had, and retiring the tester disk-wide is `rm -rf boot/grub/memtest` — the same gesture as deleting an entry file. Ubuntu's four-way `$grub_platform`/`cpuid` block is deliberately not reproduced: the same `mt86+x64` image boots through `linux` on both firmware paths, and those guards exist only to choose between it and `mt86+ia32`, which a toolkit deploying amd64 never needs. Each entry is a GUI/TTY pair whose command line is **derived from the target's own `/etc/default/grub`** (`GRUB_CMDLINE_LINUX` then `GRUB_CMDLINE_LINUX_DEFAULT`, `root=` stripped and restated from `NEW_UUID_ROOT`), so every machine keeps its own quirks; `probe_menu_cmdline()` reads the same values before the confirmation gate — usually for free, off the mount `probe_source_swapfiles()` already made — so the summary shows the command line the disk will boot with. **`NEW_UUID_BOOT` is "the UUID of the filesystem that holds `/boot`"** — the `/boot` partition's when there is one, and `NEW_UUID_ROOT` when there is not (never empty: `awk`'s `gsub("", x)` matches at every character position) — and it is what the entry's `search` uses, with the kernel path (`/boot/vmlinuz` or `/vmlinuz`) to match. When the target root is *reformatted*, the entry keyed to the UUID that partition held before (`TGT_ROOT_UUID_NOW`, read before Phase 2) is deleted: that filesystem no longer exists, so neither should the menu line advertising it.
6. **Verify + teardown** — `verify_install()` PASS/FAIL-checks the UUID translation in fstab and grub.cfg, that fstab mounts `/boot` by `NEW_UUID_BOOT` (or has no `/boot` entry at all, per `TGT_SEP_BOOT`), that grub.cfg searches the `/boot` filesystem when there is a separate one, the ESP (GRUB's module directories under `boot/grub`, this system's `entries/<root-uuid>.cfg` with the right root and `/boot` UUIDs in it, the master sourcing that file, the memtest entry when the ESP carries the image, and **every system registered there before the run still registered** — rebuilding a shared master is the one step that could quietly unregister the machines this install was not about, which is what `probe_esp_menu()` recorded beforehand for), the presence of a kernel under `/boot` (the backstop for a source that hides `/boot` some way the Phase 3 guard cannot see, and the one thing a layout change can silently lose), the root filesystem's label when `--target-root-label` asked for one (and only then — an `--update` onto a disk this toolkit never labelled is entitled to whatever it carries), the swap files (each rebuilt one is fully allocated — `swapfile_ok()` — and each dropped one is gone and disabled in fstab), and that each dropped cache is absent from the target (the check that would catch an `--exclude=` regression, which leaves the target's stale copy in place instead of deleting it), dying on any failure (the target may not boot). fstab's stale-UUID checks use `absent_active()`, which ignores commented-out lines — a `/boot` entry inherited from a source and disabled by `rewrite_fstab()` legitimately still carries the old UUID. The stale-boot-UUID check itself runs only when `SRC_SEP_BOOT` *and* the UUID actually changed — otherwise `OLD_UUID_BOOT` is the root UUID, which an in-place root legitimately still carries. The written filesystems then get `fstrim` (skipped when `supports_discard()` says the medium can't, e.g. spinning disks, or when `--no-trim` is given), followed by recursive unmount and loop-device detach if one was used. The trim is not cosmetic on a loop target: the loop driver turns discards into `FALLOC_FL_PUNCH_HOLE` on the backing file — which is exactly why `lsblk -bdno DISC-GRAN /dev/loopN` reports 4096 rather than 0 — so a `fallocate`d `.img` only becomes sparse if it runs. The **ext4** roles are trimmed only under `--update`, though: otherwise they were just `mkfs.ext4`'d, and mke2fs's `discard` extended option (the default) already discarded the whole partition, after which the rsync only ever *allocates* — no block returns to free, so the closing trim would re-discard ranges the mkfs had discarded, at real cost on slow flash. Under `--update` the filesystem is kept and `rsync --delete` genuinely frees blocks, so the trim is the only thing reclaiming them — and a separate `/boot` is trimmed on exactly the same terms as root. The **ESP** is the exception in the other direction and is trimmed on every run (formatting or not — a kept one has just had its menu and modules rewritten): `mkfs.fat` has no discard of its own, so a fresh 256 MiB ESP holding a few MiB of bootloader is released only here — on a loop-backed `.img` that is the difference between a sparse and a solid ESP. Finally two advisory `grub-fstest` probes run on the now-unmounted filesystems, because GRUB reads two of them at boot: `"$TGT_EFI" ls /boot/grub/grub.cfg` (the menu, via GRUB's FAT driver) and then the kernel the entry names — `"$TGT_ROOT" ls /boot/vmlinuz`, or `"$TGT_BOOT" ls /vmlinuz` when there is a separate `/boot` — via its ext2 driver, falling back to listing the directory so a driver that will not follow the `vmlinuz` symlink is not reported as a broken disk. GRUB's own drivers are the authority on whether the disk will actually boot.

### Conventions to follow when editing

- **Helper functions read caller-set globals** rather than taking all inputs as parameters (e.g. `rewrite_fstab()`, `rewrite_grub_distributor()`, and `run_chroot_block()` read `TGT_ROOT`, `MNT`, `SRC`, `OLD_UUID_*`/`NEW_UUID_*`, `TGT_MODEL`, `TGT_GRUB_DISK`; `rewrite_fstab()` and `verify_install()` additionally read `TGT_SEP_BOOT`/`SRC_SEP_BOOT` and the `*_UUID_BOOT` pair; `scan_swapfiles()`/`rebuild_swapfiles()` read `SRC`, `MNT`, `EXCLUDE_FROM`, `FSTAB_TABLE` and fill `SWAPFILES`, `SWAPFILES_DROPPED`, `SWAPFILES_REBUILT`, `SWAP_EXCLUDES`, `SWAPFILE_REAL`, which `rewrite_fstab()` and `verify_install()` then read; `write_esp_menu()` reads `MNT`, `TGT_MODEL`, `TGT_ROOT`, `TGT_SEP_BOOT`, `NEW_UUID_ROOT`/`NEW_UUID_BOOT`, `TGT_ROOT_UUID_NOW` and, in a dry run, `MENU_CMDLINE_PREVIEW`/`ESP_MENU_ENTRIES`/`MEMTEST_SRC`/`MEMTEST_OFF`/`ESP_MEMTEST`, which `probe_menu_cmdline()`/`probe_memtest()`/`probe_esp_menu()` filled before the confirmation gate and `verify_install()` re-reads afterwards; `sync_esp_memtest()` and `esp_master_text()` take the grub directory as an argument, being about the ESP rather than about this rootfs) — set the variables before the call. `fstab_realpath()`, `cache_drop_paths()` and `exclude_rules_unmatchable()` read `FSTAB_TABLE`, the source's mount layout that `probe_source_layout()`/`scan_cache_drops()` build with `fstab_mount_table()`, plus `SRC`/`EXCLUDE_FROM`, and fill `CACHE_PREVIEW`/`CACHE_DROPS`/`CACHE_FILTERS`/`EXCLUDE_AUDIT`/`EXCLUDE_PROBED`. `cache_filters_for()` and `rsync_pattern_escape()` are the exceptions in the other direction: both take their input as arguments, because both have two callers that must agree. `report_fstab_disables()` is passed the record file `rewrite_fstab()` just filled, but reads the target topology through `target_disks()` like everything else. `scan_disk_roles()` is the exception: it takes a variable *prefix* and writes `<PREFIX>_BIOS/_EFI/_ROOT` via `printf -v`, so one scanner serves both sides.
- **Naming:** `SRC_*` = source partitions, `TGT_*` = target partitions, `OLD_UUID_*`/`NEW_UUID_*` = pre/post-format UUID pairs, `MNT`/`SRC` = target/source root mount points (private per-instance temp dirs by default; `--mnt`/`--src` pin them).
- **Never let an absent role fall through as an empty string.** `readlink` here is uutils coreutils, whose `readlink -f ""` prints the working directory and exits 0, so `same_dev "" ""` compares equal and `add_lock ""` would take an exclusive flock on the cwd; and `awk`'s `gsub("", x)` matches at every character position. `TGT_BIOS`, `SRC_BOOT` and `TGT_BOOT` are the optional roles — gate on `[ -n "$TGT_BIOS" ]` and on the `SRC_SEP_BOOT`/`TGT_SEP_BOOT` flags (which exist precisely so no code path has to test the strings), and keep every `OLD_UUID_*`/`NEW_UUID_*` non-empty (`*_UUID_BOOT` falls back to the root UUID rather than to `""`).
- Use `die()` for fatal errors, `info()` (`==> …`) for progress, and route destructive commands through `run()` so `--dry-run` keeps working.
- **The pre-confirmation summary is built from `summary_row()`/`role_row()`**, which share one 10-column label field — that is what keeps `EFI:`, `/ (root):` and `swap:` aligned; pass an empty label for a continuation line (the swap block prints one row per swap file under a single `swap:` label). `role_row()` shows `source -> target` for a migrated/synced role and just the device for an in-place one, since which source partition feeds which target is the thing worth checking before a multi-hour transfer. The `EFI:` row is the exception to `role_row()` — the ESP is never copied from the source, so it reads `FORMAT`/`KEEP` and names one device — and the `Menu:` block continues under empty labels with the entry this run registers, the command line it will boot with, and every system already registered on that ESP that it keeps (a title already taken by a different root filesystem warns and suggests `--brand`). The `/boot` row is three-way: a `role_row()` when the target has one (its source side reading `inside / on $SRC_ROOT` when the source did not), an explicit `FLATTEN … -> the root filesystem` line when the source had one and the target does not, and `in the root filesystem` when neither does — a layout conversion is exactly the thing a reader must not have to infer. `human_size()` formats bytes for display only — nothing parses its output.
- Partition-suffix differences are handled by `partition_prefix()` (returns `p` for `nvme`/`mmcblk`/`loop`, empty otherwise) — use it rather than hardcoding `sda1` vs `nvme0n1p1`.

### Filesystem optimization (intentional, don't "fix")

The root ext4 is created with `-O sparse_super2` and a very high bytes-per-inode ratio (~4 MiB/inode, floor 1.5 M inodes), which requires a modern kernel. `--inodes-root N` pins the `mkfs.ext4 -N` count instead of deriving it (a `k`/`M` suffix multiplies the *count*, not a size; an explicit value skips the floor). It is validated right after argument parsing, alongside `--exclude-from` and `--target-root-label` (at most 16 *bytes*, since ext4's `s_volume_name` has no room for a terminator and `mke2fs` would silently truncate; `boot` refused outright, because `scan_disk_roles()` skips a `boot`-labelled partition on purpose and a root filesystem wearing that label could never be found by a scan again), so a typo fails before any disk is touched. `orphan_file` and `metadata_csum_seed` were deliberately **removed** from that list: `orphan_file` sets the dynamic `INCOMPAT_ORPHAN_PRESENT` superblock flag while orphan entries exist and only clears it on clean unmount, so an unclean shutdown leaves an incompat flag set — recoveries after power loss lost noticeably more than before. Don't add them back.

Because the root filesystem carries nothing GRUB cannot parse (`-O sparse_super2`), a separate `/boot` buys nothing in *readability* — which is why it is not the default, and why a plain deploy puts `/boot` inside `/`. What it still buys is *reachability*: a BIOS too old to boot from NVMe can only load the kernel from a disk it can address, which is the one reason `--source-boot`/`--target-boot` exist. GRUB 2.14 reads the root filesystem — verifiable without booting anything, using GRUB's own driver:

```bash
grub-fstest Ubuntu26-16GB.img ls '(loop0,gpt3)/boot/vmlinuz'  # image: root is p3
sudo grub-fstest /dev/sdX3 ls /boot/vmlinuz                   # a deployed disk
sudo grub-fstest /dev/sdX3 ls /vmlinuz                        # ...with a separate /boot
sudo grub-fstest /dev/sdX2 ls /boot/grub/                     # the menu, on the ESP
sudo grub-fstest /dev/sdX2 ls /boot/grub/entries/             # ...one file per rootfs
sudo grub-fstest /dev/sdX2 ls /boot/grub/memtest/              # ...and the memory tester
```

The kernel is what the root filesystem has to give GRUB now that the menu lives on the ESP, which is why the closing probe asks for `vmlinuz` rather than `grub.cfg`. A generated menu file is also checkable without any disk at all — `grub-script-check /boot/efi/boot/grub/grub.cfg` runs GRUB's own parser over it.

### `run_chroot_block` bootloader gating

`run_chroot_block` reads `INSTALL_GRUB_BIOS`/`INSTALL_GRUB_EFI` (default `1` if unset) to decide whether to run each `grub-install`, and always runs `update-grub` + `update-initramfs`. `install.sh` sets `INSTALL_GRUB_BIOS=1` only when a BIOS target is given, so a migration that names no BIOS Boot partition leaves the legacy bootloader byte-intact. **`INSTALL_GRUB_EFI` is now always 1:** the ESP carries GRUB's boot directory and the shared menu, and this system's entry has to be registered there whatever else the run does, so there is no such thing as a migration that leaves the ESP untouched. Both `grub-install`s pass `--boot-directory=/boot/efi/boot`. It also expands `$TGT_GRUB_DISK` unconditionally in the chroot heredoc, so any caller must set that variable even when not reinstalling BIOS GRUB.
