# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A small toolkit of Bash scripts for deploying a custom, performance-optimized Ubuntu 26.04 LTS system onto portable storage (SSD / image file). The produced disk boots on **both** UEFI and legacy BIOS machines from a single GPT layout. There is no application code — the deliverable is the scripts plus the methodology documented in `README.md` and `Portable-SSD-README.md`.

## Running the scripts

There is no build, test, lint, or CI setup — scripts are run directly and require `sudo` (they shell out to `parted`, `mkfs`, `losetup`, `chroot`, `grub-install`, etc.). Always preview destructive runs with `--dry-run`, which prints every wrapped command instead of executing it. Run with no arguments (and no `TARGET`/`TGT_*` in the environment, which would be a legitimate env-var-driven invocation) and it prints `--help` instead of marching into Phase 1 and failing on the *default* source path.

- **`install.sh`** — the single, universal entry point. Source can be a unified block device, a `.img` file (auto-attached via `losetup -P`), or scattered source partitions (`--source-efi/-root`, which may live on different disks); target can be a unified device (it partitions + formats) or scattered partitions (`--target-efi`/`--target-root` required, `--target-bios-boot` optional). **`/boot` always lives inside `/`, on both sides** — separate-`/boot` support was removed outright, since root and `/boot` were already formatted with the same ext4 feature set and GRUB reads both, so the partition bought nothing. A source that still keeps `/boot` on a filesystem of its own is *refused* (Phase 3 checks the mounted source's fstab before any copying); a leftover `/boot` partition on a target disk is ignored and left unused. Roles are found by GPT type GUID and filesystem label (`scan_disk_roles()`), never by partition number, so any other partition on either disk — data, swap, another distro, an obsolete `boot`-labelled one — is none of the script's business. Each role is left in place (target == source), migrated (target differs → reformat + full copy), or — under `--update` — synced (target differs → keep the existing filesystem, `rsync --delete` onto it). `--update` subsumes the old disk-to-disk clone (`backup.sh`, removed): it refreshes an already-installed clone incrementally instead of rebuilding it. `--exclude-from FILE` passes `rsync --exclude-from`, omitting listed paths from the copy (e.g. an impersonal clone); combined with `--update` it also adds `--delete-excluded`, so those paths are purged from the target rather than protected. If the file lists the system's swap file (as `exclude-personal.txt` does), that swap file is dropped rather than re-created and its fstab entry is commented out — an exclude file builds a deliberately swapless minimal disk. `--brand NAME` overrides the GRUB menu branding; without it, `--update` keeps the brand already stamped into the target's `/etc/default/grub` (probed via a transient read-only mount before rsync overwrites the file, so it also shows under `--dry-run`), and only otherwise is the reported model of the disk holding the target rootfs used (which can be a USB card reader's name instead of the card's).
  ```bash
  # Fresh 3-partition disk (BIOS Boot, ESP, root):
  ./install.sh --image Ubuntu26-Portable-16GB.img --target /dev/sda
  ./install.sh --image Ubuntu26-Portable-16GB.img --target /dev/sda --dry-run
  # Deploy from the running machine's own disk. nvme0n1 also carries a large
  # data partition; it is ignored, because root is found by its 'root' label:
  ./install.sh --source /dev/nvme0n1 --target /dev/sdd --update
  # Incrementally sync a split-disk source (sda EFI + nvme root) onto sdb:
  ./install.sh --source-efi /dev/sda2 --source-root /dev/nvme0n1p1 \
               --target-bios-boot /dev/sdb1 --target-efi /dev/sdb2 \
               --target-root /dev/sdb3 --update
  # Impersonal clone — deploy minus the paths listed in exclude-personal.txt:
  ./install.sh --image Ubuntu26-Portable-16GB.img --target /dev/sda \
               --exclude-from exclude-personal.txt
  ```

Verifying a change: there's no test harness, so validate by running the script against a throwaway `.img` (create one with `truncate`/`dd`, attach with `losetup -P`) under `--dry-run` first, then for real against a loop device or scratch disk.

## Architecture

`install.sh` is a single self-contained script (the former `portable-common.sh` library was folded into it, and the `init-disk.sh`/`backup.sh` helpers were removed). It sets `set -euo pipefail` and defines the `run()` dry-run wrapper (it quotes args with `%q`).

The pipeline:

1. **Resolve source/target topology** — unified device, image (loop), or scattered partitions. `scan_disk_roles <disk> <PREFIX>` scans a whole disk and fills `<PREFIX>_BIOS/_EFI/_ROOT` by GPT type GUID (`GUID_BIOS`/`GUID_EFI`/`GUID_LINUX`, defined near the top of the script) and filesystem label. Root is the Linux partition labelled `root` (which this toolkit's own `mkfs` always writes); failing that, a *lone* unlabelled Linux partition. **Everything else on the disk is ignored** — a data partition, a swap, another distro's rootfs, or an obsolete `boot`-labelled partition from the four-partition era (skipped explicitly, since it is certainly not a root filesystem and should not make the disk look ambiguous). **Ambiguity is an error, never a guess:** two or more unlabelled candidates with no `root` label dies naming them and pointing at `--source-root`/`--target-root` or `e2label`. An earlier version instead claimed the first unclaimed Linux partition as `/boot`, which silently adopted a 721 GB data partition — and on a non-`--update` run would have `mkfs.ext4 -L boot`'d it. It is used for a unified source **and** for a unified `--target` under `--update`, where the existing layout must be discovered rather than imposed (a fresh `--target` instead gets the canonical `p1`/`p2`/`p3`). Individually-named partitions are checked with `validate_partition_type()`. In a dry run no loop device is attached, so `scan_image_roles_dryrun()` reads an image's partition table with `parted -sm` straight out of the file (no root, no loop); it cannot see filesystem labels there (parted's name field is the GPT partition name, `primary` for everything this toolkit creates), so it takes the *first* Linux partition as root and warns when there is more than one candidate — it only feeds the dry run's printed summary. Any target role that is currently mounted (or active swap) is refused up front — a second mount of an in-use filesystem would succeed and let the sync write into it.
2. **Prepare target** — `parted` GPT layout (BIOS Boot 1 MiB, then the ESP — 256 MiB unless `--target-efi-size` says otherwise — then root to 100%) + `mkfs`, skipped per-role for in-place roles and skipped entirely under `--update` (which keeps the existing filesystems and `rsync --delete`s onto them). `--target-efi-size` only reaches `parted`, so it is *rejected* rather than silently ignored under `--update` or with individual `--target-*` partitions; its `k`/`M`/`G` suffixes denote a size (bare = MiB) and must resolve to whole MiB, since root starts where the ESP ends.
3. **Mount + sync** — mounts target RW (`$MNT` and `$MNT/boot/efi`; `$MNT/boot` is an ordinary directory) and source RO (`$SRC`, …), then a per-role `rsync -ahHAX --inplace --numeric-ids -x --verbose` (one rsync per migrated/synced filesystem) with the live-filesystem exclusions on root. **`-S` is deliberately absent** and only `--sparse` adds it back: every hole rsync punches is one more entry in the file's ext4 extent tree, and a large VM image is perforated by thousands of tiny ones. Measured on a 51.8 GiB `.vdi` (`/usr/local/bin/sparse_mapper.py`, which walks it with `SEEK_DATA`/`SEEK_HOLE`): 12,309 holes, 82% of them ≤ 64 KiB and worth 0.137 GiB between them, 1.01 GiB saved in total — 2% of the file — in exchange for ~11,900 extra extents. That pushed the extent tree from one level to two (a 4 KiB leaf block holds 340 entries, the inode's root holds 4), so every `fsck.ext4 -f` offered to optimize it and every read walked the extra level; fully allocated the same file needs ~415 extents, purely from the 128 MiB per-extent cap. Across the whole 459 GiB source root, sparseness was worth 1.36 GiB (0.3%). Writing the nulls out costs a couple of percent more I/O — don't reinstate `-S` as the default. Every command in this phase — the mounts and the rsyncs alike — goes through `run()`, so a dry run prints the exact command lines rather than a one-line summary: the assembled option set is the thing worth reviewing before committing to a multi-hour transfer. Only the parts that need the mounted source are skipped in a dry run (`scan_swapfiles`/`rebuild_swapfiles`, i.e. the per-swap-file `--exclude=`, whose absence from the printed command is announced), and `MOUNTS_DONE` stays 0 so `cleanup()` has nothing to unmount. The shared `RSYNC_OPTS` array gains `--delete` only under `--update`, `--exclude-from=FILE` when `--exclude-from` is given, and `--delete-excluded` when both apply (so excluded paths are purged from, not protected on, the target). Because `--exclude-from` paths are anchored to each transfer root, the personal `/…` paths in the file only match during the root rsync.
   `/boot` gets no pass of its own: it is an ordinary directory on both sides and rides along with the root rsync. `-x` is what keeps that transfer out of the target's mounted ESP at `$MNT/boot/efi` — it stops the sender crossing the boundary *and* stops `--delete` recursing across it on the receiving side, which is why no explicit protect filter is needed. Right after the source root is mounted, `fstab_mounts_boot "$SRC/etc/fstab"` refuses a source that keeps `/boot` on a filesystem of its own: the root rsync would otherwise copy an empty mount point and the target would boot to nothing. The source's own fstab is the authority (whatever its partition table looks like), and it can only be read once mounted — so a dry run announces that it cannot check this.
   Swap **files** are the one thing never transferred: the file is one multi-gigabyte run of zeros, so copying it ships gigabytes over a slow link to produce what `fallocate` makes from metadata alone — and under `--sparse`, `-S` would punch it full of holes and `swapon` then refuses it at boot (`skipping - it appears to have holes`). `scan_swapfiles()` reads the source's fstab (`swapfile_entries()` picks out plain-path `swap` entries — devices, `UUID=`, zram are ignored), excludes each of them from the root rsync, and asks rsync itself — `swapfile_excluded()`, a one-file `--dry-run` against a deliberately non-existent destination so the quick check can't skip an already-synced file — whether an `--exclude-from` rule drops it. Kept ones are re-created afterwards by `rebuild_swapfiles()` (`rm` + `fallocate` to the source file's exact size + `chown`/`chmod 600` + `mkswap`, preserving the source's label and UUID); dropped ones are neither copied nor re-created, since an exclude file is used to build a deliberately swapless minimal disk. All of that happens in Phase 3, *after* the confirmation gate, so `probe_source_swapfiles()` runs the same `swapfile_entries()`/`swapfile_excluded()` pair over a transient read-only mount of the source root beforehand and fills `SWAP_PREVIEW`: the summary would otherwise print "swap: none" about a disk that is about to receive a multi-gigabyte swap file. It is skipped when `MIGRATE_ROOT` is 0 (no root transfer means no rebuild) and degrades to "could not be read here" when the source root is not a mountable block device — a dry run against an image, which has no loop device attached.
4. **Translate identifiers** — `rewrite_fstab()` rewrites old→new UUIDs and disables any inherited `/boot` entry (done *before* the substitutions, which would otherwise rewrite it into a bogus "mount the root filesystem at `/boot`" line) — a cheap backstop behind the Phase 3 source guard. Comment lines are passed through untouched, *before* the foreign-UUID disabler: Ubuntu's stock fstab header mentions `UUID=`, and an earlier version tagged it `# [PORTABLE-SYNC-DISABLED]` on every single sync. The disabled-line handler also un-tags a payload that is itself a comment, so an fstab already damaged that way heals on the next sync. It also comments out the entries of swap files dropped by `--exclude-from` (so a swapless disk does not boot into a failing `swapon`), retargets the existing UUID-based swap entry to `NEW_UUID_SWAP` in place (appending one only if none exists, and dropping stale disabled swap lines), and comments out foreign mounts / binds (tagged `# [PORTABLE-SYNC-DISABLED]`, never re-prefixed on later syncs, keeping only the `/tmp → /var/tmp` bind); `rewrite_grub_distributor()` stamps the resolved brand (`--brand` override, the target's pre-sync `GRUB_DISTRIBUTOR` value under `--update` — read by `probe_target_brand()` right after lock acquisition — or the target disk model) into the GRUB menu branding.
5. **Chroot + bootloader** — `run_chroot_block()` bind-mounts `/dev /dev/pts /proc /sys /run`, installs GRUB for **both** `i386-pc` (BIOS) and `x86_64-efi --removable` (UEFI), writes a universal `/boot/efi/EFI/BOOT/grub.cfg` routing stub keyed to `NEW_UUID_ROOT`, then `update-grub` + `update-initramfs -u -k all`. The root filesystem is the one holding `/boot`, so the stub's `if [ -f ($root)/boot/grub/grub.cfg ]` branch is the one that fires; the `else` arm is kept (four lines) only so the stub stays usable for rescue on a disk that does carry a separate `/boot`.
6. **Verify + teardown** — `verify_install()` PASS/FAIL-checks the UUID translation in fstab and grub.cfg, that fstab has no live `/boot` entry, the EFI routing stub, the presence of a kernel under `/boot` (the backstop for a source that hides `/boot` some way the Phase 3 guard cannot see), and the swap files (each rebuilt one is fully allocated — `swapfile_ok()` — and each dropped one is gone and disabled in fstab), dying on any failure (the target may not boot). fstab's stale-UUID checks use `absent_active()`, which ignores commented-out lines — a `/boot` entry inherited from a source and disabled by `rewrite_fstab()` legitimately still carries the old UUID. The written filesystems then get `fstrim` (skipped when `supports_discard()` says the medium can't, e.g. spinning disks, or when `--no-trim` is given), followed by recursive unmount and loop-device detach if one was used. The trim is not cosmetic on a loop target: the loop driver turns discards into `FALLOC_FL_PUNCH_HOLE` on the backing file — which is exactly why `lsblk -bdno DISC-GRAN /dev/loopN` reports 4096 rather than 0 — so a `fallocate`d `.img` only becomes sparse if it runs. The **ext4** roles are trimmed only under `--update`, though: otherwise they were just `mkfs.ext4`'d, and mke2fs's `discard` extended option (the default) already discarded the whole partition, after which the rsync only ever *allocates* — no block returns to free, so the closing trim would re-discard ranges the mkfs had discarded, at real cost on slow flash. Under `--update` the filesystem is kept and `rsync --delete` genuinely frees blocks, so the trim is the only thing reclaiming them. The **ESP** is the exception in the other direction and is trimmed on every run: `mkfs.fat` has no discard of its own, so a fresh 256 MiB ESP holding a few MiB of bootloader is released only here — on a loop-backed `.img` that is the difference between a sparse and a solid ESP. Finally an advisory `grub-fstest "$TGT_ROOT" ls /boot/grub/grub.cfg` runs on the now-unmounted filesystem: GRUB's own ext2 driver is the authority on whether the disk will actually boot.

### Conventions to follow when editing

- **Helper functions read caller-set globals** rather than taking all inputs as parameters (e.g. `rewrite_fstab()`, `rewrite_grub_distributor()`, and `run_chroot_block()` read `TGT_ROOT`, `MNT`, `SRC`, `OLD_UUID_*`/`NEW_UUID_*`, `TGT_MODEL`, `TGT_GRUB_DISK`; `scan_swapfiles()`/`rebuild_swapfiles()` read `SRC`, `MNT`, `EXCLUDE_FROM` and fill `SWAPFILES`, `SWAPFILES_DROPPED`, `SWAPFILES_REBUILT`, `SWAP_EXCLUDES`, which `rewrite_fstab()` and `verify_install()` then read) — set the variables before the call. `scan_disk_roles()` is the exception: it takes a variable *prefix* and writes `<PREFIX>_BIOS/_EFI/_ROOT` via `printf -v`, so one scanner serves both sides.
- **Naming:** `SRC_*` = source partitions, `TGT_*` = target partitions, `OLD_UUID_*`/`NEW_UUID_*` = pre/post-format UUID pairs, `MNT`/`SRC` = target/source root mount points (private per-instance temp dirs by default; `--mnt`/`--src` pin them).
- **Never let an absent role fall through as an empty string.** `readlink` here is uutils coreutils, whose `readlink -f ""` prints the working directory and exits 0, so `same_dev "" ""` compares equal and `add_lock ""` would take an exclusive flock on the cwd; and `awk`'s `gsub("", x)` matches at every character position. `TGT_BIOS` is the remaining optional role — gate on `[ -n "$TGT_BIOS" ]`, and keep every `OLD_UUID_*`/`NEW_UUID_*` non-empty.
- Use `die()` for fatal errors, `info()` (`==> …`) for progress, and route destructive commands through `run()` so `--dry-run` keeps working.
- **The pre-confirmation summary is built from `summary_row()`/`role_row()`**, which share one 10-column label field — that is what keeps `EFI:`, `/ (root):` and `swap:` aligned; pass an empty label for a continuation line (the swap block prints one row per swap file under a single `swap:` label). `role_row()` shows `source -> target` for a migrated/synced role and just the device for an in-place one, since which source partition feeds which target is the thing worth checking before a multi-hour transfer. `human_size()` formats bytes for display only — nothing parses its output.
- Partition-suffix differences are handled by `partition_prefix()` (returns `p` for `nvme`/`mmcblk`/`loop`, empty otherwise) — use it rather than hardcoding `sda1` vs `nvme0n1p1`.

### Filesystem optimization (intentional, don't "fix")

The root ext4 is created with `-O sparse_super2` and a very high bytes-per-inode ratio (~4 MiB/inode, floor 1.5 M inodes), which requires a modern kernel. `--inodes-root N` pins the `mkfs.ext4 -N` count instead of deriving it (a `k`/`M` suffix multiplies the *count*, not a size; an explicit value skips the floor). It is validated right after argument parsing, alongside `--exclude-from`, so a typo fails before any disk is touched. `orphan_file` and `metadata_csum_seed` were deliberately **removed** from that list: `orphan_file` sets the dynamic `INCOMPAT_ORPHAN_PRESENT` superblock flag while orphan entries exist and only clears it on clean unmount, so an unclean shutdown leaves an incompat flag set — recoveries after power loss lost noticeably more than before. Don't add them back.

Because the root filesystem carries nothing GRUB cannot parse (`-O sparse_super2`), there is nothing left for a dedicated GRUB-safe `/boot` partition to buy — which is why separate-`/boot` support was removed rather than merely defaulted off. GRUB 2.14 reads it — verifiable without booting anything, using GRUB's own driver:

```bash
grub-fstest Ubuntu26-16GB.img ls '(loop0,gpt4)/'          # image, partition 4
sudo grub-fstest /dev/sdX3 ls /boot/grub/                 # a deployed disk
```

### `run_chroot_block` bootloader gating

`run_chroot_block` reads `INSTALL_GRUB_BIOS`/`INSTALL_GRUB_EFI` (default `1` if unset) to decide whether to run each `grub-install`, and always runs `update-grub` + `update-initramfs`. `install.sh` sets them per-role (`INSTALL_GRUB_BIOS=1` only when a BIOS target is given; `INSTALL_GRUB_EFI=$MIGRATE_EFI`) so a partial (e.g. rootfs-only) migration can leave the EFI/BIOS bootloaders byte-intact, while a full clone or whole-disk sync reinstalls both. It also expands `$TGT_GRUB_DISK` unconditionally in the chroot heredoc, so any caller must set that variable even when not reinstalling BIOS GRUB.
