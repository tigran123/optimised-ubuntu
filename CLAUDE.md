# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A small toolkit of Bash scripts for deploying a custom, performance-optimized Ubuntu 26.04 LTS system onto portable storage (SSD / image file). The produced disk boots on **both** UEFI and legacy BIOS machines from a single GPT layout. There is no application code — the deliverable is the scripts plus the methodology documented in `README.md` and `Portable-SSD-README.md`.

## Running the scripts

There is no build, test, lint, or CI setup — scripts are run directly and require `sudo` (they shell out to `parted`, `mkfs`, `losetup`, `chroot`, `grub-install`, etc.). Always preview destructive runs with `--dry-run`, which prints every wrapped command instead of executing it. Run with no arguments (and no `TARGET`/`TGT_*` in the environment, which would be a legitimate env-var-driven invocation) and it prints `--help` instead of marching into Phase 1 and failing on the *default* source path.

- **`install.sh`** — the single, universal entry point. Source can be a unified block device, a `.img` file (auto-attached via `losetup -P`), or scattered source partitions (`--source-efi/-root`, plus an optional `--source-boot`, which may live on different disks); target can be a unified device (it partitions + formats) or scattered partitions (`--target-efi`/`--target-root` required, `--target-bios-boot`/`--target-boot` optional). A separate `/boot` is **optional on both sides**: no `--source-boot`/`--target-boot` (and no such partition on a unified disk) means `/boot` is a directory inside `/`, which is what a fresh `--target` now gets — root and `/boot` are formatted with the same ext4 feature set and GRUB reads both, so the partition buys nothing. An existing disk's layout is *detected* (`scan_disk_roles()`), not assumed, so a clone that still has a separate `/boot` keeps it, and pointing a run at a target with (or without) a `/boot` partition converts the layout in either direction. Each role is left in place (target == source), migrated (target differs → reformat + full copy), or — under `--update` — synced (target differs → keep the existing filesystem, `rsync --delete` onto it). `--update` subsumes the old disk-to-disk clone (`backup.sh`, removed): it refreshes an already-installed clone incrementally instead of rebuilding it. `--exclude-from FILE` passes `rsync --exclude-from`, omitting listed paths from the copy (e.g. an impersonal clone); combined with `--update` it also adds `--delete-excluded`, so those paths are purged from the target rather than protected. If the file lists the system's swap file (as `exclude.txt` does), that swap file is dropped rather than re-created and its fstab entry is commented out — an exclude file builds a deliberately swapless minimal disk. `--brand NAME` overrides the GRUB menu branding; without it, `--update` keeps the brand already stamped into the target's `/etc/default/grub` (probed via a transient read-only mount before rsync overwrites the file, so it also shows under `--dry-run` — the one real action a dry run performs), and only otherwise is the reported model of the disk holding the target rootfs used (which can be a USB card reader's name instead of the card's).
  ```bash
  # Fresh 3-partition disk (BIOS Boot, ESP, root) — /boot ends up inside /,
  # even when the image itself still carries a separate /boot partition:
  ./install.sh --image Ubuntu26-Portable-16GB.img --target /dev/sda
  ./install.sh --image Ubuntu26-Portable-16GB.img --target /dev/sda --dry-run
  # Incrementally sync a split-disk source (sda EFI/boot + nvme root) onto an
  # sdb that still has its own /boot partition:
  ./install.sh --source-efi /dev/sda2 --source-boot /dev/sda3 \
               --source-root /dev/nvme0n1p1 \
               --target-bios-boot /dev/sdb1 --target-efi /dev/sdb2 \
               --target-boot /dev/sdb3 --target-root /dev/sdb4 --update
  # Same source, but folded onto a 3-partition sdb (no --target-boot):
  ./install.sh --source-efi /dev/sda2 --source-boot /dev/sda3 \
               --source-root /dev/nvme0n1p1 \
               --target-bios-boot /dev/sdb1 --target-efi /dev/sdb2 \
               --target-root /dev/sdb3
  # Impersonal clone — deploy minus the paths listed in exclude.txt:
  ./install.sh --image Ubuntu26-Portable-16GB.img --target /dev/sda \
               --exclude-from exclude.txt
  ```

Verifying a change: there's no test harness, so validate by running the script against a throwaway `.img` (create one with `truncate`/`dd`, attach with `losetup -P`) under `--dry-run` first, then for real against a loop device or scratch disk.

## Architecture

`install.sh` is a single self-contained script (the former `portable-common.sh` library was folded into it, and the `init-disk.sh`/`backup.sh` helpers were removed). It sets `set -euo pipefail` and defines the `run()` dry-run wrapper (it quotes args with `%q`).

The pipeline:

1. **Resolve source/target topology** — unified device, image (loop), or scattered partitions. `scan_disk_roles <disk> <PREFIX>` scans a whole disk and fills `<PREFIX>_BIOS/_EFI/_BOOT/_ROOT` by GPT type GUID (`GUID_BIOS`/`GUID_EFI`/`GUID_LINUX`, defined near the top of the script) and filesystem label (`boot`/`root`, which this toolkit's own `mkfs` always writes), falling back to on-disk order — a *lone* unclaimed Linux partition is root, since `/boot` inside `/` is the default layout. It is used for a unified source **and** for a unified `--target` under `--update`, where the existing layout must be discovered rather than imposed (a fresh `--target` instead gets the canonical `p1`/`p2`/`p3`). It dies only on a missing ESP or root; a missing `/boot` is legal. Individually-named partitions are checked with `validate_partition_type()`. In a dry run no loop device is attached, so `scan_image_roles_dryrun()` reads an image's partition table with `parted -sm` straight out of the file (no root, no loop) to get the role numbers right. Any target role that is currently mounted (or active swap) is refused up front — a second mount of an in-use filesystem would succeed and let the sync write into it.
   `SRC_SEP_BOOT`/`TGT_SEP_BOOT` record whether each side keeps `/boot` on its own filesystem; every `/boot` site is gated on those flags rather than on an empty `SRC_BOOT`/`TGT_BOOT` string, because uutils' `readlink -f ""` resolves to the *working directory* and exits 0 (so `same_dev "" ""` is true and `add_lock ""` would lock the cwd).
2. **Prepare target** — `parted` GPT layout (BIOS Boot 1 MiB, then the ESP — 256 MiB unless `--target-efi-size` says otherwise — then root to 100%) + `mkfs`, skipped per-role for in-place roles and skipped entirely under `--update` (which keeps the existing filesystems and `rsync --delete`s onto them). `--target-efi-size` only reaches `parted`, so it is *rejected* rather than silently ignored under `--update` or with individual `--target-*` partitions; its `k`/`M`/`G` suffixes denote a size (bare = MiB) and must resolve to whole MiB, since root starts where the ESP ends.
3. **Mount + sync** — mounts target RW (`$MNT`, `$MNT/boot` only when the target has a separate `/boot`, `$MNT/boot/efi`) and source RO (`$SRC`, …), then a per-role `rsync -ahHAXS --inplace --numeric-ids -x` (one rsync per migrated/synced filesystem, with `--info=progress2` on a tty and `-q` otherwise) with the live-filesystem exclusions on root. The shared `RSYNC_OPTS` array gains `--delete` only under `--update`, `--exclude-from=FILE` when `--exclude-from` is given, and `--delete-excluded` when both apply (so excluded paths are purged from, not protected on, the target). Because `--exclude-from` paths are anchored to each transfer root, the personal `/…` paths in the file only match during the root rsync.
   `BOOT_PASS` decides whether `/boot` needs a transfer of its own: it is 0 exactly when the source's `/boot` filesystem *is* the target's (both sides keep `/boot` inside `/`, so the root rsync carries it along; or both use the same `/boot` partition), and 1 otherwise — two different `/boot` partitions, or a layout being converted in either direction. When it is 1 the root rsync carries `--filter='- /boot/'` **and** `--filter='P /boot/'`: the exclude hides `/boot` from the sender, and the explicit *receiver-side* protect rule is what stops `--delete` from emptying the target's `/boot` before the second pass refills it. A plain exclude would not do — `--delete-excluded` demotes unqualified rules to sender-side only. The `/boot` pass itself protects `/efi/` the same way, since `$MNT/boot` may now be an ordinary directory rather than a mount point that `-x` would shield.
   Swap **files** are the one thing never transferred: `-S` would punch the swap file full of holes and `swapon` then refuses it at boot (`skipping - it appears to have holes`). `scan_swapfiles()` reads the source's fstab (`swapfile_entries()` picks out plain-path `swap` entries — devices, `UUID=`, zram are ignored), excludes each of them from the root rsync, and asks rsync itself — `swapfile_excluded()`, a one-file `--dry-run` against a deliberately non-existent destination so the quick check can't skip an already-synced file — whether an `--exclude-from` rule drops it. Kept ones are re-created afterwards by `rebuild_swapfiles()` (`rm` + `fallocate` to the source file's exact size + `chown`/`chmod 600` + `mkswap`, preserving the source's label and UUID); dropped ones are neither copied nor re-created, since an exclude file is used to build a deliberately swapless minimal disk.
4. **Translate identifiers** — `rewrite_fstab()` rewrites old→new UUIDs, disables the inherited `/boot` entry when the target keeps `/boot` inside `/` (done *before* the substitutions, which would otherwise rewrite it into a bogus "mount the root filesystem at `/boot`" line) and conversely inserts one — directly after the `/` entry, never appended, since `mount -a` walks fstab in order and a `/boot` line after `/boot/efi` would bury the ESP — when the target has a separate `/boot` and the source did not. The old→new `/boot` substitution is guarded by `map_boot`, since without a separate source `/boot` `OLD_UUID_BOOT` *is* `OLD_UUID_ROOT` and would consume the root entry first. It also comments out the entries of swap files dropped by `--exclude-from` (so a swapless disk does not boot into a failing `swapon`), retargets the existing UUID-based swap entry to `NEW_UUID_SWAP` in place (appending one only if none exists, and dropping stale disabled swap lines), and comments out foreign mounts / binds (tagged `# [PORTABLE-SYNC-DISABLED]`, never re-prefixed on later syncs, keeping only the `/tmp → /var/tmp` bind); `rewrite_grub_distributor()` stamps the resolved brand (`--brand` override, the target's pre-sync `GRUB_DISTRIBUTOR` value under `--update` — read by `probe_target_brand()` right after lock acquisition — or the target disk model) into the GRUB menu branding.
5. **Chroot + bootloader** — `run_chroot_block()` bind-mounts `/dev /dev/pts /proc /sys /run`, installs GRUB for **both** `i386-pc` (BIOS) and `x86_64-efi --removable` (UEFI), writes a universal `/boot/efi/EFI/BOOT/grub.cfg` routing stub keyed to `NEW_UUID_BOOT`, then `update-grub` + `update-initramfs -u -k all`. `NEW_UUID_BOOT` means "the UUID of the filesystem that holds `/boot`" — the `/boot` partition when there is one, the root UUID otherwise — so the stub needs no special case: its existing `if [ -f ($root)/boot/grub/grub.cfg ]` branch picks `/boot/grub` or `/grub` accordingly. Keeping it non-empty also keeps `rewrite_fstab()`'s `gsub` off an empty regex, which would match at every character position.
6. **Verify + teardown** — `verify_install()` PASS/FAIL-checks the UUID translation in fstab and grub.cfg, the EFI routing stub, the presence of a kernel under `/boot` (which a layout conversion is the one thing that could silently lose), and the swap files (each rebuilt one is fully allocated — `swapfile_ok()` — and each dropped one is gone and disabled in fstab), dying on any failure (the target may not boot). fstab's stale-UUID checks use `absent_active()`, which ignores commented-out lines — a `/boot` entry disabled by a collapse legitimately still carries the old UUID. The written filesystems then get `fstrim` (skipped when `supports_discard()` says the medium can't, e.g. spinning disks, or when `--no-trim` is given), followed by recursive unmount and loop-device detach if one was used. The trim is not cosmetic on a loop target: the loop driver turns discards into `FALLOC_FL_PUNCH_HOLE` on the backing file — which is exactly why `lsblk -bdno DISC-GRAN /dev/loopN` reports 4096 rather than 0 — so a `fallocate`d `.img` only becomes sparse if it runs. The **ext4** roles are trimmed only under `--update`, though: otherwise they were just `mkfs.ext4`'d, and mke2fs's `discard` extended option (the default) already discarded the whole partition, after which the rsync only ever *allocates* — no block returns to free, so the closing trim would re-discard ranges the mkfs had discarded, at real cost on slow flash. Under `--update` the filesystem is kept and `rsync --delete` genuinely frees blocks, so the trim is the only thing reclaiming them. The **ESP** is the exception in the other direction and is trimmed on every run: `mkfs.fat` has no discard of its own, so a fresh 256 MiB ESP holding a few MiB of bootloader is released only here — on a loop-backed `.img` that is the difference between a sparse and a solid ESP. Finally, when the target has no separate `/boot`, an advisory `grub-fstest "$TGT_ROOT" ls /boot/grub/grub.cfg` runs on the now-unmounted filesystem: GRUB's own ext2 driver is the authority on whether the disk will actually boot.

### Conventions to follow when editing

- **Helper functions read caller-set globals** rather than taking all inputs as parameters (e.g. `rewrite_fstab()`, `rewrite_grub_distributor()`, and `run_chroot_block()` read `TGT_ROOT`, `MNT`, `SRC`, `OLD_UUID_*`/`NEW_UUID_*`, `TGT_SEP_BOOT`, `TGT_MODEL`, `TGT_GRUB_DISK`, `NEW_UUID_BOOT`; `scan_swapfiles()`/`rebuild_swapfiles()` read `SRC`, `MNT`, `EXCLUDE_FROM` and fill `SWAPFILES`, `SWAPFILES_DROPPED`, `SWAPFILES_REBUILT`, `SWAP_EXCLUDES`, which `rewrite_fstab()` and `verify_install()` then read) — set the variables before the call. `scan_disk_roles()` is the exception: it takes a variable *prefix* and writes `<PREFIX>_BIOS/_EFI/_BOOT/_ROOT` via `printf -v`, so one scanner serves both sides.
- **Naming:** `SRC_*` = source partitions, `TGT_*` = target partitions, `OLD_UUID_*`/`NEW_UUID_*` = pre/post-format UUID pairs, `*_SEP_BOOT` = "this side keeps /boot on its own filesystem", `MNT`/`SRC` = target/source root mount points (private per-instance temp dirs by default; `--mnt`/`--src` pin them).
- **Never let an absent role fall through as an empty string.** `readlink` here is uutils coreutils, whose `readlink -f ""` prints the working directory and exits 0, so `same_dev "" ""` compares equal and `add_lock ""` would take an exclusive flock on the cwd; and `awk`'s `gsub("", x)` matches at every character position. Gate on `SRC_SEP_BOOT`/`TGT_SEP_BOOT`, and keep `OLD_UUID_BOOT`/`NEW_UUID_BOOT` populated (they fall back to the root UUID).
- Use `die()` for fatal errors, `info()` (`==> …`) for progress, and route destructive commands through `run()` so `--dry-run` keeps working.
- Partition-suffix differences are handled by `partition_prefix()` (returns `p` for `nvme`/`mmcblk`/`loop`, empty otherwise) — use it rather than hardcoding `sda1` vs `nvme0n1p1`.

### Filesystem optimization (intentional, don't "fix")

The root ext4 is created with `-O sparse_super2` and a very high bytes-per-inode ratio (~4 MiB/inode, floor 1.5 M inodes), which requires a modern kernel. `--inodes-root N` pins the `mkfs.ext4 -N` count instead of deriving it (a `k`/`M` suffix multiplies the *count*, not a size; an explicit value skips the floor). It is validated right after argument parsing, alongside `--exclude-from`, so a typo fails before any disk is touched. `orphan_file` and `metadata_csum_seed` were deliberately **removed** from that list: `orphan_file` sets the dynamic `INCOMPAT_ORPHAN_PRESENT` superblock flag while orphan entries exist and only clears it on clean unmount, so an unclean shutdown leaves an incompat flag set — recoveries after power loss lost noticeably more than before. Don't add them back.

Because the root and `/boot` feature sets are now identical (`-O sparse_super2`; a separate `/boot` differs only in inode density and label), there is nothing left for a dedicated GRUB-safe `/boot` partition to buy, which is why `/boot` inside `/` is the default layout. GRUB 2.14 reads it — verifiable without booting anything, using GRUB's own driver:

```bash
grub-fstest Ubuntu26-16GB.img ls '(loop0,gpt4)/'          # image, partition 4
sudo grub-fstest /dev/sdX3 ls /boot/grub/                 # a deployed disk
```

### `run_chroot_block` bootloader gating

`run_chroot_block` reads `INSTALL_GRUB_BIOS`/`INSTALL_GRUB_EFI` (default `1` if unset) to decide whether to run each `grub-install`, and always runs `update-grub` + `update-initramfs`. `install.sh` sets them per-role (`INSTALL_GRUB_BIOS=1` only when a BIOS target is given; `INSTALL_GRUB_EFI=$MIGRATE_EFI`) so a partial (e.g. rootfs-only) migration can leave the EFI/BIOS bootloaders byte-intact, while a full clone or whole-disk sync reinstalls both. It also expands `$TGT_GRUB_DISK` unconditionally in the chroot heredoc, so any caller must set that variable even when not reinstalling BIOS GRUB.
